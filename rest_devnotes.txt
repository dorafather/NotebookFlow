NotebookFlow rest.sce 개발 이력 노트
====================================
목적: rest.sce 인라인에 누적되던 긴 claude-code 개발이력 주석(각 티켓의
배경/근거/실측 결과 설명)을 별도 파일로 분리해, rest.sce 자체는 로직만
빠르게 훑어볼 수 있도록 정리한다.

주의: React 프론트엔드의 "저장" 버튼을 누르면 rest.sce가 구조화 데이터로부터
재직렬화되며 파일 내 모든 주석(이 파일로 옮기고 남긴 한 줄 주석 포함)이
사라진다(데이터/블록 수는 무손실). 따라서 이 문서가 rest.sce 주석의
유일한 보존처다 - 프론트엔드 저장을 거친 뒤에는 이 파일만 신뢰할 것.

형식: 시간순. 각 항목에 관련 처리::/전송::/문장:: 이름을 표기.

[2026-09-12] (사용자 승인) 처리::GITHUB.깃허브이슈순회
업무지침: 업무지침_GitHub이슈처리_CPH_LOOP_재작성.md
--------------------------------------------------------------------
기존에는 배열 개수가 가변(0개~N개)인데 인덱스 0~9만 NULL 가드 처리::로
펼쳐(깃허브이슈제목추가0~9, 아래에서 전부 제거) 10개까지만 대응했다 -
리포지토리 이슈가 10개를 넘으면 그 이상은 조용히 누락되는 구조적 한계가
있었다. 함수.반복(LOOP)+함수.컴프리헨션(CPH) 조합도 검토했으나, CPH는
필드를 "이름"이 아니라 row[fieldIdx] 오디널 위치로만 뽑아(EXEFUNC.cpp
EXE_CPH) GitHub API JSON의 필드 순서가 바뀌면 조용히 깨지는 취약한
설계가 된다.
대신 이번에 EXEPARAM.cpp에 추가한 "세션.객체.이름[인덱스].필드" 대괄호
참조(인덱스 자리에 세션 변수 허용 - 사용자에게 유틸 기능 추가 승인받음)를
이용해 처리:: 자기 자신을 재귀 호출하며 배열 끝(대괄호 인덱스가 범위를
벗어나 값이 빈 값이 되어 "!= NULL" 조건이 거짓이 되는 시점)까지 개수
제한 없이 순회한다 - 10개 상한이 사라진다(실측: 11개로 검증, 검증 4).
함수.객체저장(gh_issues, 수신메시지.결과)로 원본 배열을 먼저 세션에
필드 이름 그대로 복사해두는 이유: EXEPARAM.cpp의 새 대괄호 헬퍼는
POOLDATA/세션을 아는 계층(RestParam 기반)이라 세션에 있는 배열만
"인덱스를 세션 변수로 동적으로 바꿔가며" 읽을 수 있다 - 수신메시지
(RestMsg) 원본을 담당하는 GETR()은 세션을 전혀 모르는 순수 JSON
트리 워커라 이 동적 인덱스 참조를 지원하지 않는다(GETR/SETR은 이번
승인 범위 밖이라 손대지 않음 - EXEPARAM.cpp 헬퍼 주석 참고).

[2026-09-12] 처리::BSKY.procBskyTokRcv
--------------------------------------------------------------------
로그인 응답 수신 시 토큰/DID 저장은 기존 동작 그대로 두고, 그 직후 이번
포스팅에 쓸 현재 시각(bsky_now)을 세션에 찍은 뒤 전송.sndUpText를
이어서 실행한다(순차 실행의 두 번째 단계). 기존에 이 처리::를 트리거하는
경로가 없었으므로(procRestInit 어디서도 sndBskyAccToken을 호출하지
않았음) 여기서 무조건 이어붙여도 회귀 위험 없음.

[실측 발견] 함수.날짜의 format 인자에 "+09:00"을 직접 섞어 넣는 방식
(함수.날짜(bsky_created,%Y-%m-%dT%H:%M:%S+09:00))을 한 번 시도했으나
격리된 단독 요청에서도 즉시 실패(record.createdAt 필드 자체가 통째로
비어 "Missing required key createdAt" 400을 받음 - trace로 직접
확인)했다 - "+" 문자가 낀 format 인자를 EXE_DATE/paramone이 온전히 한
덩어리로 못 받는 것으로 보인다(libUtil 범위 밖이라 원인을 더 깊이 파지
않고 되돌림). 대신 원래 방식(포맷 문자열엔 "+"를 넣지 않고 함수.날짜로
시각만 세션에 저장 → 문장::로 +09:00을 덧붙여 조합)이 더 안정적으로
동작함을 재확인(격리 재검증 통과)했다.

[2026-09-12] 전송::BSKY.sndUpText
--------------------------------------------------------------------
기존 테스트 스텁 3곳 교체 + 실측 중 발견한 추가 버그 1건(범위 밖이지만
실제 포스팅 성공을 위해 필수라 함께 수정):
1) repo = 1(플레이스홀더) → 세션.bsky_did(로그인 응답 did, 실제 계정
   식별자) - AT Protocol createRecord는 repo에 유효한 DID/handle을
   요구하므로 "1"은 그대로 두면 실제 포스팅이 항상 실패한다(업무지침
   3번 목록엔 없었지만 실제 성공적인 포스팅을 위해 반드시 필요해 함께
   수정 - 보고서 참고).
2) 헤더[0].val: 기존에도 세션.bsky_access를 참조하고는 있었으나 "Bearer "
   접두사가 빠져 있었다(GITHUB/NOTION 인증 헤더는 문장::로 접두사를
   붙이는데 BSKY만 원본 토큰 그대로 - AT Protocol은 반드시 "Bearer
   <accessJwt>" 형식을 요구하므로 이 상태로는 항상 401. 문장::
   bskyAuthHeader로 접두사를 붙이도록 수정 - 이것도 업무지침 3번
   목록엔 명시 안 됐지만 동일한 이유로 필수 수정).
3) record.text = 세션.post_message(트리거 시 저장한 실제 문구)
4) record.createdAt = 문장.bskyCreatedAt(아래 참고 - 매번 현재 시각)
5) [실측 발견] 전송메시지.XXX = 리터럴값 형태로 RHS에 "."이 포함된
   문자열을 직접 대입하면(주소.경로/collection/$type) ACTIONPARSER가
   첫 "." 앞부분만 남기고 잘라버린다(실측: 주소.경로
   "/xrpc/com.atproto.repo.createRecord"가 "/xrpc/com"으로, collection
   "app.bsky.feed.post"가 "app"으로 잘려 실제 요청이 501을 받음 -
   trace로 직접 확인). 반면 문장::로 감싼 값(예: 기존 문장::BSKY.actk,
   이번 티켓의 문장::BSKY.bskyCreatedAt)은 트레이스에서 정상 확인됨
   (예: 로그인 주소는 100% 정상 전달) - 문장:: 블록은 파싱 시점에
   통째로 하나의 토큰으로 저장돼 이 잘림 문제를 피해간다. libUtil
   (ACTIONPARSER.cpp)은 이번 작업 범위 밖이라 수정하지 않고, "." 포함
   리터럴은 전부 문장::로 감싸는 방식으로 우회했다(주소.경로/collection/

(이 버그는 project_notebookflow_actionparser_dot_truncation_bug 메모리
참고 - 2026-09-12 EXEPARAM.cpp의 "." 포함 리터럴 복원 수정으로 근본

[2026-09-12] 문장::BSKY.bskyCreatedAt
--------------------------------------------------------------------
TIME::PRINT()(EXEFUNC.cpp EXE_DATE)는 내부적으로 localtime_r 기반이라
UTC를 직접 뽑을 수 있는 함수가 .sce에 노출돼 있지 않다(libUtil은 이번
작업 범위 밖이라 수정하지 않음 - 필요하면 별도 티켓으로 보고). 이 PC는
KST(UTC+9, DST 없음, `Get-TimeZone`으로 실측 확인)로 고정 운영되므로,
로컬시각을 "Z"(UTC)로 거짓 표기하는 대신 실제 오프셋 +09:00을 그대로
붙인다 - RFC3339/ISO8601 모두 유효한 형식이라 AT Protocol createdAt
파싱에 문제없다.

[agent_flow.py run_claude() 버그 수정] claude -p --output-format json은
인증 실패 등으로 exit code 1이 나도 stdout에 유효한 JSON({"is_error":
true,"result":"실제 원인 문구"})을 그대로 남긴다(실측 확인). 기존 코드는
returncode!=0이면 stdout을 전혀 안 보고 "claude 종료 코드 1: "+빈 stderr
로만 응답해 실제 원인이 사라졌다 - JSON 파싱을 항상 먼저 시도하고, 그게
실패할 때만(진짜 크래시 등 JSON 자체가 없는 경우) exit code/stderr 기반
메시지로 폴백하도록 고쳤다.

개인 TELEGRAM 봇에서 "고객문의 {문의내용}"을 받으면, 이미 검증된
"네임스페이스 경계를 넘는 자유 호출" 원칙(Telegram↔GitHub 조합과 동일한
패턴)으로 NOTEBOOKFLOW_BOT의 기존 전송::NOTEBOOKFLOW_BOT.NF봇그룹메시지
전송을 그대로 재사용해 커뮤니티 그룹으로 전달한다. 새 전송:: 오브젝트는
만들지 않았고, 세션.nfbot_group_message도 기존 것을 그대로 재사용했다
(FLOW.이벤트명==NF봇그룹메시지전송 트리거와 동일 변수 - "rest" 세션이
전역 공유라는 기존에 알려진 특성상 이론적 경합 가능성은 있으나, 두 트리거
모두 짧은 처리:: 한 블록 안에서 저장→전송이 즉시 끝나 실질적 위험은
낮다고 판단, 별도 변수 분리는 하지 않음).

처리::TELEGRAM.텔레그램에코응답처리의 함수.앞자리비교 목록에

사용자에게는 기존 전송::TELEGRAM.델레그램응답전송(문장.텔레그램응답문장
